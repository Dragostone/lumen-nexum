Die Funktion entfernt Leerraum am Rand und fasst mehrere Leerzeichen, Tabs oder Zeilenumbrüche zu einem Leerzeichen zusammen. Wörter, Zahlen, Großschreibung und Satzzeichen bleiben erhalten. Das Original wird separat aufbewahrt.

      
      
Drei Testfälle mit unterschiedlichen Aufgaben
Nutze die drei Fälle als Testreihe. Halte jeweils vor dem Ausführen fest, welche Veränderung du erwartest und welcher Inhalt erhalten bleiben muss. Vergleiche dann die Ausgabe Zeichen für Zeichen. Für den zweiten Durchlauf entscheidest du vorab: Darf eine bereits normalisierte Ausgabe noch einmal verändert werden? Begründe deine Antwort mit dem Zweck dieser Funktion.
  1.   My card was not charged 42 euros.  : Prüfe Rand-Leerzeichen und die fachlich wichtigen Angaben not und 42.
  2. My card was charged twice.: Hier gibt es nichts aufzuräumen. Prüfe, ob die Funktion trotzdem eingreift.
  3. Schreibe I did NOT receive 25 euros. mit einem Zeilenumbruch nach NOT und mehreren Leerzeichen vor 25. Entscheide, welcher Fehler durch diesen Fall auffallen würde, aber durch den ersten Fall unentdeckt bliebe.
Wenn dein Ergebnis abweicht
Vergleiche zuerst das Original mit deiner eingegebenen Zeichenfolge. Verwechsle einen sichtbaren Zeilenumbruch nicht mit den zwei Zeichen \n. Die Darstellung im Ausgabefeld zeigt Text als JSON-Zeichenfolge. Das Wort NOT darf nicht verschwinden.

      
      
Prüfe auch einen Text, der bereits aufgeräumt ist.

    

    

      
03 / ÜBER DIE GRENZE
Optional: echtes lokales HTTP

      
Eine Frage raus.
Eine Antwort zurück.

Baue zuerst die Normalisierungsroute
Dein Starter enthält zunächst nur GET /health. Deshalb ergänzen wir jetzt die Route selbst. Öffne fallfinder/src/server.ts im Editor. Wenn du bisher nur den Starter angelegt hast, ersetze seinen Inhalt durch den folgenden kleinen Server. Wenn du schon eigene Änderungen hast, übernimm nur die fehlenden Importe, Middleware und /normalize-Route.
Datei: src/server.ts
Vollständigen Servercode anzeigen
import { Hono } from 'hono';
import { serve } from '@hono/node-server';
import { cors } from 'hono/cors';
import { bodyLimit } from 'hono/body-limit';

const app = new Hono();
// Lokales Lehrlabor ohne echte Kundendaten. Keine öffentliche Bereitstellung.
app.use('*', cors());
app.use('*', bodyLimit({ maxSize: 4096 }));
app.get('/health', c => c.json({ project: 'Fallfinder', ready: true }));
app.post('/normalize', async c => {
  let input: unknown;
  try { input = await c.req.json(); }
  catch { return c.json({ error: 'JSON erforderlich.' }, 400); }
  if (!input || typeof input !== 'object' || !('text' in input)
      || typeof input.text !== 'string' || input.text.length > 500
      || input.text.trim().length === 0) {
    return c.json({ error: 'text: 1 bis 500 Zeichen, nicht nur Leerraum.' }, 422);
  }
  const original = input.text;
  const normalized = original.trim().replace(/\s+/g, ' ');
  return c.json({ original, normalized, changed: original !== normalized });
});
const server = serve({ fetch: app.fetch, hostname: '127.0.0.1', port: Number(process.env.PORT ?? 3217), overrideGlobalObjects: false });
console.log('Fallfinder: http://localhost:' + (process.env.PORT ?? 3217));
process.on('SIGINT', () => server.close());
process.on('SIGTERM', () => server.close());

  1. cors() erlaubt der separat geöffneten Lernoberfläche, eine Antwort zu lesen. Diese offene Einstellung gehört nur zu unserem lokalen Lehrlabor mit ausgedachten Daten.
  2. bodyLimit({ maxSize: 4096 }) begrenzt den gesamten Request auf 4096 Bytes. Die zusätzliche Prüfung von 500 Zeichen begrenzt den Nachrichtentext. Bytes und Zeichen sind verschiedene Größen.
  3. c.req.json() liest den Request. Unlesbares JSON liefert 400. Fehlendes, nicht textförmiges, zu langes oder leeres text liefert 422.
  4. original behält die Eingabe. Nur normalized erhält die bereinigte Kopie. changed vergleicht beide Zeichenfolgen.
  5. serve(...) startet den Server an 127.0.0.1:3217. Das ist der lokale Rechner, kein veröffentlichter Kundendienst.
Speichere die Datei. Beende nur deinen eigenen laufenden Server mit Strg+C. Prüfe und starte im Projektordner:
node --check src/server.ts
npm start
Öffne ein zweites Terminal im selben Arbeitsplatz. Die folgenden Befehle sind für Bash oder Git Bash. -i zeigt die Statuszeile; -H kennzeichnet JSON; -d sendet den Request-Inhalt.
curl -i http://localhost:3217/normalize -H 'Content-Type: application/json' -d '{"text":"  My card was not charged 42 euros.  "}'
curl -i http://localhost:3217/normalize -H 'Content-Type: application/json' -d '{"text":"   "}'
Erwarte zuerst 200 und die Felder original, normalized, changed. Beim zweiten Aufruf erwarte 422 mit einer Erklärung. Vergleiche die tatsächlichen Antworten, bevor du mit den Schaltflächen unten weitermachst.
Wenn dein Terminal auf einem anderen Lernrechner läuft als der Browser, meint localhost jeweils einen anderen Rechner. Nutze dann die Terminalaufrufe als eigenen HTTP-Nachweis. Eine fehlgeschlagene Browserverbindung ist kein Beleg dafür, dass die Normalisierung falsch ist.

      
Browsersendet JSON→Backendprüft & normalisiert→Responseliefert JSON

      
POST ist die HTTP-Methode. /normalize ist die Route, also die Adresse dieser Aufgabe im Backend. JSON ist ein Textformat für Daten. Im Feld text steht deine Nachricht. Ablauf untersuchen

      
Was wir senden
POST http://localhost:3217/normalize
Starte vorher den Server aus der Starter-Anleitung. Der Klick sendet nur an deinen eigenen Rechner. Verwende ausgedachte Nachrichten.
Noch keine Anfrage gesendet.

      
Der Server antwortet nicht?
Prüfe im Server-Terminal, ob er auf Port 3217 läuft. Lies die Fehlermeldung. Starte ihn nach der Starter-Anleitung und sende denselben Text erneut. Die Simulation bleibt verfügbar, ist aber kein Beleg für einen laufenden Server.

      
      
Vorhersagen, senden, vergleichen
Führe zwei echte Requests durch, wenn dein Normalisierungs-Endpunkt ergänzt und gestartet ist. Andernfalls kennzeichne die Beobachtung ausdrücklich als Simulation und hole die Serverprüfung später nach.
  1. Sende einen Satz mit not und einer Zahl. Notiere Status und vollständige Antwort.
  2. Ändere in Station 2 die Eingabe zu drei Leerzeichen. Sende sie erneut.
  3. Sende den gültigen Satz noch einmal. Damit prüfst du, ob der Server nach dem Fehler weiterarbeitet.
Status lesen
200 meldet einen erfolgreichen HTTP-Aufruf. In unserer Normalisierungsroute bedeutet 422: Der Server hat die Anfrage gelesen, lehnt aber den Inhalt ab. 404 kann darauf hinweisen, dass die Route im eigenen Starter noch fehlt. Eine Verbindungsfehlermeldung ohne HTTP-Status belegt keine Serverantwort.
Eine Pause passt jetzt: 5 Minuten.
Speichere deine Antworten. Du kannst danach mit den Fallkarten weiterarbeiten; es läuft kein Timer.

Echten Modelllauf prüfen

      
Was das Modell später ergänzt
Ein Embedding ist eine Zahlenliste, mit der das Modell Text darstellt. Fallfinder kann diese Listen vergleichen und Beispiele mit ähnlicher Darstellung finden. Das verwendete Modell Xenova/bge-small-en-v1.5 ist für englische Texte gedacht.
Die Textbereinigung aus Schritt 2 und die Normalisierung eines Vektors sind zwei verschiedene Aufgaben. Ein hoher Ähnlichkeitswert ist keine Wahrscheinlichkeit dafür, dass ein Fall richtig gelöst ist.
Für die Übergabe an den Support reicht die passende Karte allein noch nicht. Zwei sichtbare Zahlungen könnten zwei Buchungen sein oder eine Vormerkung neben einer Buchung. Entscheide, welche Information du zuerst anfordern oder prüfen würdest. Halte in deiner Antwort fest, welchen nächsten Arbeitsschritt diese Information begründet und was weiterhin offenbleibt. Der Ähnlichkeitswert erledigt die Buchprüfung nicht nebenbei.
Eine mögliche Prüffrage
Sind tatsächlich zwei Buchungen entstanden oder ist eine davon nur vorgemerkt? Ähnliche Formulierungen beantworten diese Frage noch nicht. Die Beispiele helfen beim Nachsehen; sie erteilen keine Freigabe.

      

Die Auswahl steht. Jetzt brauchen die Beispiele stabile IDs.
